# Qwen + OpenRouter: material latency/cost optimizations for multimodal PDF-heading extraction

## Qwen vision detail controls, batching, structured output, reasoning, and caching

### Takeaway
Qwen provides several material controls beyond payload-byte trimming: `max_pixels` directly constrains visual-token count; non-thinking mode can materially cut response time and output-token charges; Qwen’s asynchronous batch inference halves real-time token prices for supported multimodal models; and context caching makes repeated long, stable prefixes far cheaper. These preserve source-bound heading semantics only if resolution/model/prompt changes are validated against the current extraction corpus, whereas structured JSON and caching can normally be semantics-preserving transport/execution changes.

### Cited Findings
- Qwen vision models resize images to the `max_pixels` bound when high-resolution mode is off. For Qwen3/Qwen3-VL-family models, one visual token corresponds to 32 x 32 pixels; Qwen documents the approximate image-token formula as scaled-height x scaled-width / token-pixels + 2. Thus `max_pixels` is a direct, high-leverage input-token/cost and prefill-latency control, rather than merely an upload-size control. [Qwen visual understanding documentation](https://help.aliyun.com/en/model-studio/vision)
- Qwen documents that lowering `max_pixels` reduces visual-token consumption for cost-sensitive cases, while raising it can retain details but accepts slower processing; its high-resolution mode fixes a much larger 16,384-visual-token ceiling and ignores `max_pixels`. The same documentation warns that high resolution can preserve fine text but high-resolution uploads may raise timeout risk; it specifically advises client-side reasonable scaling rather than assuming larger images improve detection accuracy. [Qwen visual understanding documentation](https://help.aliyun.com/en/model-studio/vision)
- Current Qwen vision documentation lists structured output as supported by Qwen3.7/Qwen3.6/Qwen3.5 and Qwen3-VL series in non-thinking mode; `qwen3.5-ocr` is specifically positioned for document/table/handwriting extraction. [Qwen vision-model capability page](https://help.aliyun.com/en/model-studio/vision-model/)
- Qwen’s JSON-object mode uses `response_format: {"type":"json_object"}` and requires the literal word “JSON” in a system or user message. The documentation cautions that an invalid result may require a separate repair call, so it is a format guard, not proof of semantic correctness. [Qwen structured-output documentation](https://help.aliyun.com/en/model-studio/qwen-structured-output)
- Qwen documents that thinking content is billed as output tokens. For hybrid-thinking models, setting `enable_thinking: false` disables it; its troubleshooting guidance says that, when thinking is not needed, disabling it significantly reduces output tokens and measured total time by 60–75%. This is a vendor-reported measured range, not a guarantee for this pipeline. [Qwen deep-thinking documentation](https://help.aliyun.com/en/model-studio/deep-thinking)
- Qwen’s newer Responses API documents `reasoning.effort` as the preferred control and says `enable_thinking` is slated for deprecation. Reasoning emits a reasoning output item; therefore a low/no-reasoning setting can reduce latency/cost but changes the inference regime and must be accuracy-tested on headings. [Qwen Responses API reference](https://help.aliyun.com/en/model-studio/qwen-api-via-openai-responses)
- Model Studio batch inference is asynchronous and documented at 50% of the real-time price for successful input and output tokens. It supports listed multimodal image/video models and `qwen-vl-ocr`, accepts up to 50,000 JSONL requests/500 MB per input file, and returns separate result/error files. This is a cost-throughput method, not a per-document latency reduction. [Qwen batch-inference documentation](https://help.aliyun.com/en/model-studio/batch-inference)
- Batch mode supports `enable_thinking` and `thinking_budget` per request body; Qwen states that several Qwen3.5–3.8 models have thinking enabled by default, making explicit disabling particularly relevant to batch extraction. Batch jobs can queue and complete only within their configured 1–14-day wait window. [Qwen batch-inference documentation](https://help.aliyun.com/en/model-studio/batch-inference)
- Qwen explicit context cache uses `cache_control: {"type":"ephemeral"}`; it requires at least 1,024 tokens, has a five-minute TTL refreshed on hit, costs typically 125% of normal input to create, and typically 10% on hits. Implicit caching also needs a 1,024-token common prefix, is not guaranteed, and is typically 20% of normal input on Model Studio-supported models. [Qwen context-cache documentation](https://help.aliyun.com/en/model-studio/context-cache)
- Qwen states explicit and implicit cache do not affect response quality. For a visual model, it recommends placing the image/video before text when asking multiple questions about the same media, but placing text before image/video when asking the same question of different media—an ordering rule that matters for cache hits. [Qwen context-cache documentation](https://help.aliyun.com/en/model-studio/context-cache)

### Inferences
- **Likely highest immediate Qwen optimization:** establish a per-page `max_pixels` floor through a heading-recall regression suite, rather than globally enabling high-resolution mode. Pages dominated by large text/clear section headings will likely tolerate a smaller visual-token budget; dense small-font pages may not. This preserves the V14/V12/V2 source-bound contract only when the same headings/page bindings are demonstrated over the evaluation corpus.
- **Safest semantic-preserving changes:** use JSON-object output for the existing extraction schema; set deterministic low-temperature settings as already appropriate; cache an unchanged long system/schema prefix; and use batching for offline documents. They do not ask the model to infer different source content, though malformed JSON/retry behavior still requires validation.
- **Conditional semantic changes:** disabling or lowering reasoning and reducing resolution affect what evidence the model can consider. Use them as a cascade: economical non-thinking/smaller-image first pass, with an unchanged high-fidelity/standard-reasoning retry only for a documented uncertainty condition. Do not silently accept lower-fidelity output as equivalent.
- **Batching recommendation:** use Model Studio batch only for backlog/reprocessing where turnaround can be asynchronous. It preserves each page’s prompt/image and output mapping through `custom_id`, so it can preserve source binding, but it is unsuitable for interactive latency or strict immediate-result contracts.

### Gaps
- Official Qwen pages identify model families and feature support, but do not publish a heading-extraction accuracy curve by `max_pixels`, reasoning effort, or batch versus real-time execution. A local labelled corpus is necessary to choose safe thresholds.
- The exact Qwen model/provider/version presently used by the pipeline was intentionally not inspected in this assignment; compatibility of each parameter must be confirmed against that chosen endpoint.

## OpenRouter caching, routing, structured outputs, telemetry, concurrency, and failure behavior

### Takeaway
OpenRouter can materially improve repeated-call cost through Qwen prompt caching and sticky `session_id` routing, and improve availability/latency through provider selection and automatic fallbacks. Response caching can make exact duplicate requests nearly instantaneous and free, but is only appropriate for an idempotent content-addressed rerun. OpenRouter’s documented routing can alter the serving provider; strict source-bound comparability may require pinning/allowlisting a validated provider or validating equivalence across allowed providers.

### Cited Findings
- OpenRouter documents Alibaba Qwen prompt-cache reads at 0.1x normal input pricing and writes at 1.25x, enabled explicitly with `cache_control`. A warm cache resides at its provider endpoint, so it only helps if subsequent requests route back to that endpoint. [OpenRouter prompt-caching guide](https://openrouter.ai/blog/tutorials/prompt-caching-sticky-routing/)
- `session_id` is documented as the sticky routing key: after the first successful request, follow-ups are routed to the provider holding the warm cache. OpenRouter advises observing `usage.prompt_tokens_details.cached_tokens`, `cache_write_tokens`, and `cache_discount` to verify actual behavior and savings. [OpenRouter prompt-caching guide](https://openrouter.ai/blog/tutorials/prompt-caching-sticky-routing/)
- The OpenRouter Chat Completions API supports `response_format`, `reasoning`/`reasoning_effort`, `provider`, `models`, `session_id`, `cache_control`, and metadata opt-in; a response includes token usage, while `X-OpenRouter-Metadata: enabled` exposes routing metadata. [OpenRouter Chat Completions API reference](https://openrouter.ai/docs/api/api-reference/chat/send-chat-completion-request?explorer=true)
- OpenRouter’s official routing guidance says `provider.sort: "latency"` prioritizes time-to-first-token, `"throughput"` prioritizes output speed, and `"price"` prioritizes cost. The `:nitro` and `:floor` suffixes are shortcuts for throughput and price sorting, respectively. [OpenRouter routing documentation](https://openrouter.ai/blog/announcements/introducing-nitro-and-floor-price-shortcuts/)
- Provider-level fallback is automatic by default (`allow_fallbacks: true`) for failures/rate limits within a model. The `models` array enables sequential cross-model fallback for context errors, moderation, rate limiting, and downtime; OpenRouter says failed attempts are not billed and the serving model/provider is billed. [OpenRouter model-routing guide](https://openrouter.ai/blog/insights/model-routing/)
- OpenRouter’s `provider` controls include `order`, `only`, `ignore`, `sort`, `max_price`, performance preferences, and `require_parameters`. The latter can constrain routing to providers that support the request parameters, relevant when preserving structured-output/caching/reasoning behavior. [OpenRouter model-routing guide](https://openrouter.ai/blog/insights/model-routing/)
- OpenRouter response caching is separate from provider prompt caching. When enabled with `X-OpenRouter-Cache: true`, an identical request may be served from OpenRouter’s edge cache without a provider call or token billing; OpenRouter reports 80–300 ms cached returns. [OpenRouter response-caching announcement](https://openrouter.ai/blog/announcements/response-caching/)
- OpenRouter exposes generation request/usage metadata through `/api/v1/generation`; its API reference exposes this endpoint, while the prompt-caching guide identifies it alongside the response usage object and Activity page as a cache-observability route. [OpenRouter generation metadata API reference](https://openrouter.ai/docs/api/api-reference/generations/get-generation); [OpenRouter prompt-caching guide](https://openrouter.ai/blog/tutorials/prompt-caching-sticky-routing/)
- OpenRouter says paid models have no plan-based rate limit; provider rate limits generally trigger fallback routing, while exceptionally high bursts can receive OpenRouter 429s. [OpenRouter pricing/limits page](https://openrouter.ai/pricing)

### Inferences
- **Best OpenRouter cache design for this workload:** put a stable extraction rubric, source-bound JSON schema, and fixed examples first; hold a stable `session_id` only within a document/job; use Qwen-compatible explicit `cache_control`; keep the page image and page-specific request last. Then prove hits through `cached_tokens` rather than assuming them. This preserves semantics if the prompt contents themselves are unchanged.
- **Response cache is a breakthrough only for exact reruns:** use `X-OpenRouter-Cache: true` only if the complete request is content-addressed (same page image bytes/URL, prompt, model, settings, schema) and the desired policy is to reuse precisely the former extraction. It is not a substitute for processing distinct pages or changed prompts.
- **Parallelism:** no official OpenRouter Batch API documentation was located in the official-source search. For latency, client-side bounded concurrent independent page calls are the available architectural inference; use a concurrency cap/backpressure and idempotent request/job keys, because the documented service can return 429 at high bursts. This does not alter page semantics if each call keeps its own page/source identifiers.
- **Routing trade-off:** `sort: latency`/`:nitro` can reduce latency, but switching provider endpoints may alter non-deterministic model output. For a source-bound V14/V12/V2 pipeline, start with a validated `provider.order`/`only` plus `require_parameters: true`; leave `allow_fallbacks` on only if fallbacks have passed the same contract suite. If deterministic endpoint provenance outweighs availability, turn fallback off and retry/queue explicitly.
- **Timeout/retry behavior:** provider failover handles its documented 5xx/rate-limit cases, but an application-level deadline, exponential retry policy, and idempotency/deduplication strategy remain necessary; official sources found did not specify a universal OpenRouter client timeout or retry schedule. A retry must retain the identical source page and correlation ID, never substitute a different page/image.
- **Telemetry gate:** record OpenRouter generation id/routing metadata, provider/model, total/prompt/completion/reasoning/cache tokens, latency, retry/fallback path, and page/source hash. This makes it possible to quantify cost/latency gains and audit that results remain linked to the exact source evidence.

### Gaps
- No official OpenRouter Batch API documentation was found in this research pass; do not assume a server-side batch discount or batch endpoint exists through OpenRouter.
- No official OpenRouter document found here specifies default client timeout values, a Retry-After contract, or exact automatic-failover latency. Treat timeout/retry configuration as application responsibility and benchmark it.
- Provider routing documentation describes operational selection, not output equivalence. There is no official guarantee that two providers serving the same Qwen model return byte- or semantically-identical extractions.
