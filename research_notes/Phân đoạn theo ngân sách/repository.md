# Khảo sát phân đoạn và ngân sách trong repository

## 1. Cách các lane phân đoạn source, chọn heading và chuyển extent sang grouping/binding

### Takeaway

Hiện repository có ba chiến lược segmentation riêng: PDF ưu tiên trang/layout block rồi giới hạn core ở 48 dòng; DOCX ưu tiên paragraph với giới hạn 48 paragraph và 28 KB compact facts; scan dùng trang hoặc khoảng paragraph suy ra từ gap, tối đa 48 dòng/core. ## 2. Request-byte, token, call, concurrency, timeout và chi phí

### Takeaway

`PreparedRequest.Bytes` là số byte UTF-8 của đúng JSON body mà `OpenRouterWire.Build` tạo; `AgentModel` hash cùng bytes rồi gửi chúng, nên đây là phép đo request đáng tin cậy ở transport boundary. Tuy nhiên vài guard/planner lại dùng estimate không đồng nhất: cost tier và token-budget check so request bytes với giá trị token; scan selection nâng byte cap lên 256 KiB nhưng budget planner vẫn dự toán spare request theo 128 KiB; hierarchy có output cap động nhưng `AgentBudget.AttemptUsd` dự trữ output như thể mọi request có cap 32,768. Stage budgets tách rời nên chưa có hard global USD ceiling cho cả extraction.

Conversation concurrency được khóa bằng `AgentBudget` thread lock cho call count/reserve, nhưng parallelism khác giữa lane và các stage phụ làm actual call geometry khác planner. Selection/grouping dùng cùng document budget; OCR, transcription, vision và hierarchy tạo budget riêng. Provider usage parser đọc prompt/completion/reasoning/cached token và cost, nhưng phần lớn token counters chỉ nằm trong `AgentModel`; selection audit chủ yếu trả calls/cost, hierarchy audit không xuất billing, nên tổng chi phí run có thể không quan sát được đầy đủ.

### Inferences

- Strongest concrete unit mismatch: `PromptTokenBudget` is enforced against request bytes, and rate-tier selection compares `requestBytes` to `MinPromptTokens`; the parser similarly compares provider token count to request bytes. The practical consequence is a dimensionality-invalid limit and tier selection, especially under Unicode/multimodal payloads where UTF-8 bytes/token is not constant. Rename/type units explicitly and use provider token usage only after response; preflight can use a calibrated tokenizer estimate with safety margin, never equate bytes with tokens.
- Scan selector can admit requests up to 262,144 bytes, but `BudgetFor` computes spare-call ceiling using 131,072-byte cost. That planner understates its own max allowed request size. Conversely hierarchy reserves 32,768 completion tokens for requests that actually ask only 256–2,144 tokens, making its $3 reserve much more conservative and capable of early refusal even when provider cost would fit.
- `ReservedUsd` intentionally remains cumulative worst-case even after actual costs arrive. This is safe against overspend if estimate is conservative, but can exhaust the ceiling prematurely; current request-bytes-as-tokens pricing and hard-coded reserve sizes make “safe” either too low or too high. A shared ledger could reserve per call from actual output cap + measured request bytes, replace reserve with provider actual at settlement, retain a bounded overrun margin, and stop on unknown billing.
- A shared design needs typed, independent caps: serialized request bytes, maximum input tokens, requested output tokens, response bytes, tool-history bytes, POST count, concurrency, deadline and USD. Do not let `ByteCap` or `PromptTokenBudget` stand in for token count. Record requested and transport-enforced output cap on every call.
- Admit should be atomic across call-count/reserve and expose a stage/call identity. Current parallel admission is safe at the counter level, but any future “release reserve/reconcile actual” must stay atomic under concurrency and must not free reserve before a POST’s billing outcome is known.
- Budget arithmetic should be generated from a call graph, not copied constants: selection turns/retries/repairs, sibling review, scan audit, grouping requests/repairs/retries, VLM/transcription, hierarchy rounds/retries. Today some share one AgentBudget, others own separate budgets, and auxiliary calls are not all modeled in the selector planner. Define per-stage ceilings plus a parent run ceiling, or require child budgets to reserve against a common parent ledger.
- Every continuation request serializes the growing history. Exact wire bytes are known at each POST; the remaining budget should be tested against that actual body each time. To avoid starting an unusable conversation, estimate bounded future growth from max tool result sizes, but never substitute estimate for exact admission. The 65,536-byte tool message cap does not itself guarantee each whole-history JSON request stays under its request-byte cap.

### Gaps

- `AgentModel` accumulates actual prompt/completion/reasoning/cached tokens internally, but no app-level artifact was located that consistently serializes all counters per stage/call. `ModelReply` stores reasoning text only through an optional diagnostics hook; raw reasoning and actual token metadata are not a routine safe audit surface.
- Placement `HeadingPlacer` has its own 400-call/$3 budget, but the returned `PlacementAudit` focuses on logical calls/decisions and omits actual USD, prompt/completion/reasoning usage. Aggregate run USD therefore undercounts or is unknown for placement.
- Scan has separate OCR, VLM, transcription, selection/grouping, and placement activity. Some diagnostics expose preflight totals and stage timings; OCR local runtime has no provider USD, while placement billing is not surfaced. A canonical run-level total must define whether retries, cache hits, local OCR and reused preflight count.
- The exact per-stage caller override for OCR parallelism and scan selector concurrency was not exhaustively traced through all CLI/API configuration surfaces. Current defaults differ (general selection 6; scan selection/VLM/transcription 32; OCR jobs use caller parallelism), so deployment rate limiting may depend on entry point.

## 3. OCR/transcription/vision, hierarchy, PDF072 page-15 qualification and design recommendations

### Takeaway

Scan is a multi-stage pipeline: local OCR builds the page/line universe; optional vision observes page typography/readings and optional transcription emits candidate text; selection/grouping then run on scan lines with selected reading and extent; hierarchy is a separate later service. These stages have different caps and budgets and cannot be treated as one single “request size.” Hierarchy placement is specifically batched by 16, asks for a dynamic output-token budget per pending row, validates exact alias coverage and earlier-parent validity, and then a deterministic resolver checks graph properties. It does not currently expose the same billing telemetry as selection.

The 072 PDF page-15 qualification demonstrates a valid operational technique: merge four adjacent core ranges into one disjoint 76-atom page core, preserve all other ranges, verify exact source coverage/order, and measure the full request at each continuation. The first packet was 103,604 bytes, and largest observed follow-up 129,943 bytes, below 131,072. This is a single-source qualification-only result, not a reusable guarantee or a causal evaluation of segmentation alone: the override changes target scope, adjacent context/facts composition, request bytes, and the model’s conversation trajectory.

### Inferences

- `103,604` initial and `129,943` largest continuation leave 27,468 bytes of headroom under 131,072 for that run; the 4 follow-up requests grew by about 26.3 KB from the first turn. This is empirical for a single packet/model/tool path, not a universal continuation-growth multiplier. The full serialized body already includes the history, and exact-body admission should remain authoritative.
- A qualification harness should pin the source SHA, alias universe SHA, evidence-store SHA, segmentation plan, exact coverage proof, prompt/model/provider SHA and each serialized request hash. Changing any of those should produce a new qualification identity. “Same bytes” alone is not enough if `SEG-n` or target identities differ; the manifest documents earlier B packet used `SEG-015` with duplicated target aliases, while the valid disjoint full run uses `SEG-014`.
- Shared adaptive packing should be a deterministic preflight and admission layer, not a semantic selector: build ordered candidate ranges using lane boundary rules; measure all exact first-turn requests; split or merge only while exact alias coverage and boundaries remain valid; then let live continuation checks enforce each new request’s byte and token/cost caps. Preserve the source snapshot plus packing plan as an auditable artifact.
- For image-heavy scan, treat image-byte length as an explicit request-byte dimension, page crop count/line count as separate semantic constraints, and prompt/completion tokens as independent budgets. A 128 KiB byte cap does not imply a fixed input-token count or output-token headroom.
- An aggregate run budget should include preflight vision/transcription, selection, any sibling review/scan audit, grouping, hierarchy and transport retries. Local OCR can contribute elapsed time/CPU budget but not provider USD; cache reuse should report zero live calls plus reused-work provenance, not fold historical cost into current run spend.
- The 072 run is a useful upper-bound observation for page 15 only: the packet approached the 128 KiB cap on its fourth selector turn yet stayed below it; the actual output was 42 headings / 26 placed / 14 unresolved, and page-15 selected headings had full-line extents. It establishes byte feasibility and one end-to-end execution, not that the packer improves heading quality or that bigger cores are always better.

### Gaps

- The qualification artifact has no formal counterfactual using the same source snapshot, same chosen aliases and same adjacent context but alternative core sizes. It therefore cannot isolate “whole page fits” from changed context, selected facts or stochastic model response.
- The `$0.031373632` reported amount is selector-only; hierarchy cost was not surfaced. The 42/26/14 metrics do not establish total provider bill or token usage for the run.
- Page-15 follow-up request sizes are measured body bytes; the stored summary does not provide a calibrated relationship between those byte sizes and prompt token counts. No global byte-to-token ratio should be inferred.
- A shared packer must decide whether to optimize only the initial request or reserve room for worst-case tool history/repairs. Current stage limits can bound continuation but not guarantee all possible continuations fit; this requires explicit policy for split-before-start versus continue-until-admission-refusal.
