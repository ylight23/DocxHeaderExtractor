# V6 D3: provider qualification plan (Issue #9), offline

Written for: the Issue #9 reviewers and the user, to decide whether a canary may be licensed.
Status: PLAN ONLY. No provider call, no freeze, no Gold change, no production change.
Baseline: commit 81a1c86 (D2.3). Metadata snapshot: `p7.f1.v6.d3-metadata-snapshot.v1.json` (draft, unverified at endpoint level).

## 1. What this plan decides and what it does not
- It defines the gates that must be satisfied before any provider call, the canary ladder, the cost ceilings, the acceptance and stop criteria, and the open issues.
- It does not license a call. A canary needs a separate written approval that names the frozen protocol SHA, the locked route, and a USD ceiling.
- Measured cost and the bounds below are for planning only. The price figures are user-supplied and unverified.

## 2. Endpoint lock (gate E)
Before any license, record in the metadata snapshot, from the provider's metadata API and not from memory:
- model ID `qwen/qwen3.7-flash`, provider ID, route name, and the fact that automatic fallback is disabled;
- endpoint context window and maximum completion tokens (the model-level 1,000,000 and 65,536 are not yet confirmed for the route);
- supported parameters: JSON response format, tools, temperature, `max_tokens`, reasoning controls;
- reasoning mode: whether thinking is on by default, whether thinking tokens count against `max_tokens`, and how the usage object reports them;
- endpoint prices, timeout, and retry behaviour.

If a route change is needed, that is a new experiment version, not a silent switch. Alibaba Cloud native may be a control arm only as a separately frozen experiment.

## 3. Token and cost measurement (gate T)
- Bytes are an upper bound on tokens for UTF-8 text. That bound is used only for pre-call checks.
- Post-call cost uses the usage object returned for each request, reconciled against the raw response hash.
- A tokenizer, or a sourced measurement of token counts for this model, is required before the freeze. Bytes divided by four is not a gate.
- Reasoning tokens are part of completion cost. The visible-output budget (16,384 bytes) does not bound them. A reasoning reserve must be fixed from the endpoint's accounting, not assumed.

## 4. Canary ladder
Each step needs its own approval and its own ceiling. A step may not start until the previous step's acceptance criteria are met and its receipts are reconciled.

| Step | Scope | Purpose | Stop if |
|---|---|---|---|
| C0 | No call. Replay the stored raw payloads of D2.3 through the response parser with recorded fixtures only | Check that parsing, budgets and manifest checks behave as in the offline tests | Any unexplained rejection |
| C1 | 073, shard 60, 3 requests | Protocol works end to end on a small document: request, response, usage, raw store, transcript | Any unparsed response, any budget breach, any mismatch between usage and the cost model |
| C2 | Segments of 094 and 024 with heading-heavy structure and the known false-negative cases of those documents. Identifiers to be listed from the frozen Gold review, not chosen here | Check whether retrieval and reopen recover known false negatives, and whether the model pages search results | Retrieval rounds exceeded in more than a stated share of nodes; reopen or search misuse above a threshold set before the run |
| C3 | 028, full document, after C1 and C2 pass | Scale check on the largest document | Any step-level stop from C1 or C2 |

Position-sensitivity runs (section 6) are a separate arm. They run only after C1 passes, on the same source set, instruction and IDs.

## 5. Acceptance and stop criteria
Acceptance is about the protocol. It is not a claim of accuracy.

Gate A (protocol, required for every canary step):
- every request has a stored raw payload and raw response, hashed, and the transcript refers to them;
- every response is either accepted under the contract or rejected with a named code; none is dropped silently;
- every accepted state has an evidence reference that was shown to the node;
- the manifest hashes match the pinned candidate hash and the source hashes;
- the usage object is stored for every request and the summed cost is within the ceiling.

Gate B (reporting, required for every canary step): report separately ProtocolResolved, EvidenceRefsPresent, PresentedShare, GlobalReviewCoverage, UnpagedSearches and UnreadMatches. A protocol result is never reported as a statement that the model read or verified the whole document.

Hard stops (the run halts and nothing is retried automatically):
1. Any provider route, model or provider ID that differs from the locked snapshot.
2. Any request whose projected worst-case cost, computed before sending, would take the total above the ceiling.
3. A missing usage object, or a usage object that cannot be reconciled with the stored response.
4. Any response with `finish_reason` indicating truncation, or reasoning tokens that exhaust the output cap before a visible answer.
5. Any INPUT_OVER_BUDGET or OUTPUT_OVER_BUDGET stop that the protocol reports for the canary document. These are reported and reviewed, not raised by changing the budget.
6. A retry rule that would send the identical body more than once after a transport or contract failure.
7. Any write to the Gold set, the production code, or the frozen protocol directory.

## 6. Position sensitivity protocol (offline design, provider runs later)
- Same source set, same instruction, same IDs. Only the position of one target candidate changes: HEAD, MIDDLE and TAIL of its prompt (local shard prompt and synthesis prompt).
- Record, per target: decision, evidence references, parent and continuation references, and final hierarchy position, for each placement.
- A difference is reported as instability. It is not corrected by the code, and no threshold is chosen in this plan.
- The offline half exists and is tested (`PromptOrder TARGET:<alias>:HEAD|MIDDLE|TAIL`).

## 7. Reproducibility
Every provider run must record:
- frozen code SHA (the commit that contains the protocol under test), and the baseline commit 81a1c86 for comparison;
- model ID, route, provider ID and the metadata snapshot hash;
- prompt and manifest hashes for each request;
- raw request and response files, with SHA-256, and a usage receipt per request;
- the canary step, the ceiling, and the approval that licensed it.

A run that cannot produce these is not evidence.

## 8. Data safety (gate S)
Open, and required before C1:
- access control on the raw directory (read and write restricted to the run owner; no sharing of raw responses outside the run);
- redaction policy for any personal or non-public text that appears in the source documents;
- retention policy for raw payloads and responses, and how they are deleted.

Source documents in the heading corpus are the experiment's inputs. Their redistribution to the provider is governed by the route's data policy, which must be recorded in the metadata snapshot.

## 9. Contract changes since D2.3
None are needed for the plan. The D2.3 follow-up changes made here are:
- Search paging is tracked per query and per node: each query has its own read range, and unread matches are counted per query, so a completed query cannot hide an unread one. Gaps are reported.
- The candidate hash now includes layout. It is the value to pin. A run reports `CandidatesPinned` true only when an expected hash was supplied and matched.
- `EvidenceComplete` is renamed `EvidenceRefsPresent`. It means each decided occurrence names an evidence reference. It does not mean the cited source was shown in full. `PresentedShare` reports the share of occurrences that appeared as text in some payload.

Pinning is recommended but not yet enforced by the code. A canary must not start unless `CandidatesPinned` is true. That check belongs in the provider runner, not in this offline code.

## 10. Known limits that remain
- Scripted models do not measure Qwen's recovery of false negatives, its use of layout, its paging behaviour, or its position sensitivity. Only a canary can measure them.
- The input budget of 131,072 bytes is an internal cap. The largest measured synthesis input is 119,246 bytes (91%). It is not a claim about the endpoint's context.
- GlobalReviewCoverage ranges from 0.5% to 56.5% per document in the scripted preflight. Most occurrences are carried without a global review. A protocol result does not change that.
- The scripted retrieval policy searches the single query `1` and reads only its first page. In the v6 preflight (`p7.f1.v6.d2-preflight.v6-retrieve-d23-pin`, structurally identical to v5), document 028 at shard 60 has 27 (node, query) pairs with unread matches and 34,101 unread matches in total. Across the 24 documents and all four shard sizes, the total is 1,192,463 unread matches. This is what partial search coverage looks like. It must not be read as "the model searched the whole document".
- `CandidatesPinned` is false in every preflight row, as expected, because the offline preflight does not pin its candidate hash.

## 11. Open issues, in order of priority
1. Endpoint lock (gate E) through the provider metadata API. Blocks everything else.
2. Tokenizer or sourced token measurement (gate T). Blocks the ceiling.
3. Reasoning mode and the reserve it needs inside `max_tokens`. Blocks the output cap.
4. Raw directory ACL, redaction and retention (gate S). Blocks C1.
5. Enforce the pinned candidate hash in the provider runner.
6. List the false-negative identifiers of 094 and 024 from the frozen Gold review for C2.
7. Decide the USD ceiling for C1 after items 1 to 3.

## 12. Decision requested
- Accept this plan as the offline basis for D3.
- Do not license any call until items 1 to 4 are closed and the snapshot records the locked endpoint.
- C1 (document 073, three requests) is the first candidate for a license, with a ceiling proposed after gate E.
