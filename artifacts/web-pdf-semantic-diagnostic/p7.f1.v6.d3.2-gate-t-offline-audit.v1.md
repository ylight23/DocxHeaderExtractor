# V6 D3.2: Gate T0 offline audit (Issue #9)

Written for: the Issue #9 reviewers, to decide what Gate T can close and what needs a separate approval.
Status: OFFLINE AUDIT. No API call, no inference, no freeze, no Gold or production change.
Baseline: commit 849c14f (D3.1b preflight v10). Model `qwen/qwen3.7-flash`. Route `alibaba` (user decision).

## 1. Summary
- Gate T0 is complete as an offline audit. Gate T is NOT closed.
- Two findings change the plan:
  1. **Routing scope.** OpenRouter documents that a base provider slug in `provider.only` matches every endpoint of that provider, including variants and regions. The lock `only: ["alibaba"]` therefore does not exclude `alibaba/us-east-1`. This must be decided by the user (section 6).
  2. **Reasoning control is unknown for this route.** OpenRouter says the `reasoning.max_tokens` budget for Alibaba Qwen thinking models varies by model. Nothing in the metadata shows that Qwen3.7 Flash on `alibaba` supports a thinking budget. The 16,384-token reserve is therefore not a verified parameter.
- The cost bound is updated to the preflight v10 counts (section 4). It is a computed ceiling under stated assumptions, not a payment limit guaranteed by the provider.

Assumptions behind these numbers, each UNKNOWN until verified:
- The tier is chosen per request by its prompt tokens (the metadata lists thresholds; the rule is not stated). The bound charges the highest tier the request's byte count reaches, which is conservative.

These are ceilings under assumptions. No USD ceiling for C1 is chosen here.

## 6. Decisions needed from the user
1. **Routing scope.** `provider.only: ["alibaba"]` matches every Alibaba endpoint, including `alibaba/us-east-1`, per S2. Options:
   - (a) accept both variants and state it; the cost bound is then the us-east-1 bound (0.2826 USD at 65,536);
   - (b) find a way to exclude the variant (for example an `ignore` list or an exact slug), which is not in the documentation read here and must be checked before use;
   - (c) choose another route. The lock recorded in snapshot v3 is therefore not exclusive to the `alibaba` tag.
2. **Reasoning mode.** No verified control exists for this route. Options: leave the endpoint default (not recommended, since it is unknown); a reasoning-off setting if one is verified; or a separately approved canary to measure it.
3. **Whether a canary is worth requesting** to measure usage, reasoning and tokens. This needs a separate approval and a USD ceiling.

## 7. Usage audit (design and offline check)
Implemented: `P7F1V6Usage.Check` reads one received response. It reads `usage.prompt_tokens`, `usage.completion_tokens`, `usage.completion_tokens_details.reasoning_tokens` (S1 names this field) and `choices[0].finish_reason`. It reports codes; it never guesses a missing field.

| Code | Meaning |
|---|---|
| OK | usage present, finish stop, consistent |
| USAGE_MISSING | no usage object: the request cannot be audited, so it cannot be accepted |
| USAGE_FIELDS_MISSING | prompt or completion count missing |
| FINISH_LENGTH | truncated by the token cap |
| REASONING_EXHAUSTED | truncated and no visible text, with reasoning using the budget |
| USAGE_INCONSISTENT | reasoning larger than completion |
| COMPLETION_OVER_CAP | completion above the max_tokens of the request |
| PROMPT_TOKENS_EXCEED_BYTES | prompt tokens above the UTF-8 size of the body, which is impossible for UTF-8 text |
| FINISH_REASON_MISSING / UNEXPECTED | any other finish reason is a stop for review |

Simulated responses (fixtures, not provider data): `p7.f1.v6.d3.2-usage-fixtures/`, 8 files covering OK, truncation with visible text, reasoning exhaustion, missing usage, inconsistent reasoning, completion over cap, prompt tokens over bytes, and absent reasoning details (kept as null, not zero). Tests: 11/11 pass on this checkout (`P7F1V6UsageD32Tests`).

The fixtures test the audit logic only. They say nothing about what the endpoint returns.

## 8. Transport requirements (design; no transport exists)
A guard in a unit test does not prove what leaves the process. The transport must, in order:
1. take the `PreparedRequest.Body` produced by `P7F1V6Protocol.Prepare`, and nothing else;
2. encode it as UTF-8 and compute SHA-256 over the **exact bytes written to the HTTP request body**, not over the string it started from;
3. refuse to send if that hash differs from `PreparedRequest.Sha256`, and record the refusal as a transport stop;
4. record the body hash, byte count, HTTP status and the response hash in the transcript;
5. send the Authorization header from the environment and never write it into a file, log or artifact.

`VerifyTransportBody` remains a check of a string. The transport requirement is that the check runs on the bytes that are sent. Until a transport is written and tested against a local mock server, the boundary is not verified.
