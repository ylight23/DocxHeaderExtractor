# V6 task-conditioned, evidence-grounded agent (Issue #9): design D0.v2, offline

Status: DESIGN ONLY. No API call, no protocol freeze, no production change, no Gold change. Replaces D0 (`p7.f1.v6.design.v1.md`), which stays in the repository for the record and is not a basis for D1.
Written for: the user and the Issue #9 reviewers. Changes are answers to the GPT-6 review "CHANGES REQUESTED".

## 0. Corrections to D0 v1
1. **V5 did keep the AT-LOCATION rule.** The V5 prompt still says "operating AT ITS OWN LOCATION" and "a line that names a heading whose content is elsewhere does not operate here". What V5 lost, compared with V4.1, is:
   - the list of competing explanations (table labels, captions, numbered provisions, front matter, form fields, administrative blocks, running headers);
   - the list of navigation lines (table of contents, list of tables, index, cross-references);
   - the sentence that the heading opening a navigation region (for example "Contents") does operate.
2. **The cause of V5's loss is not established.** V5 also changed the unit of reasoning (regions before headings), the JSON output, the coverage requirement and the selection behaviour. The missed title headings (034, 064, 060) are consistent with losing the navigation-opener sentence, but that is a hypothesis.

## 1. Hypotheses and the controlled test that would settle them
- **H1:** losing the navigation-opener sentence and the navigation list causes the errors on title headings that sit on navigation pages (034, 064, 060).
- **H2:** losing the competing-explanations list causes the false positives on table labels, captions and front matter (049, 044, 087).
- **H3:** the region-first unit itself, independent of the prompt, causes some of the loss.

Controlled comparison on the same documents, chunks, tools and plan shape:
- **Arm A:** V5 as run (region-first, current prompt). Already measured: F1 0.799.
- **Arm B:** V5 with the V4.1 competing-explanations list and the navigation-opener sentence restored. Only the prompt text changes. Tests H1 and H2 together.
- **Arm C:** V4.1 as measured (direct per-line, F1 0.868). The reference.
- A and B differ only in prompt text, so B − A estimates the prompt effect. Comparing B with C tests whether the unit change (H3) matters once the prompt is restored.

Nothing here is run yet. Arm B needs its own protocol version, plan and authorization, and its cost is part of the cap the user approves.

## 2. Do not fix V4.1 verbatim: split the guidance
The V4.1 list is useful as knowledge, but it mixes three kinds of content. V6 separates them.

| Kind | Where it lives | Example |
|---|---|---|
| **General reasoning principles** (in the base prompt, all tasks) | Base system prompt | Consider competing explanations. Check the position, the neighbouring context and the source evidence. Do not infer a heading from bold, size or numbering alone. Every decision needs source evidence. |
| **Location check** (in the base prompt, all tasks) | Base system prompt | A line counts as a heading at its source location only when it names or opens content here. A line that names content elsewhere does not operate here. The heading that opens a navigation region is a question for the task (see below), not a rule of the base prompt. |
| **Task criteria** (from the user's instruction, per run) | Interpretation written by Qwen, checked by the experiment | Which headings to take, which levels, whether forms, tables or figures count. |

Policy that belongs to one bench (for example, whether "Form No. 02" is a heading) is never in the base prompt. It is in the task definition of that bench. The 087 conflict is therefore resolved in the MAIN_HEADINGS or HEADING_MEMBERSHIP definition, not by editing the base prompt.

## 3. Three components instead of a closed task enum
| Component | Set by | Content |
|---|---|---|
| `originalUserInstruction` | the user, immutable | The verbatim request, stored with its SHA-256. Never paraphrased by code. |
| `modelTaskInterpretation` | Qwen, free text | What Qwen understands the request to mean, the scope it applies, and the parts it cannot resolve. No fixed target values. |
| `evaluationTrack` | the experiment configuration, fixed before the run | The bench that selects the Gold, for example `HEADING_MEMBERSHIP_DEV24`. It is for scoring only and does not limit which headings the system may understand. |

Technical status values only: `COMPLETE`, `INCOMPLETE`, `CLARIFICATION_REQUIRED`, `NOT_ANSWERABLE`. They say what state the answer is in, not what kind of heading may be returned.

Mismatch: a separate evaluation step compares `modelTaskInterpretation` with the `evaluationTrack` and reports the mismatches. C# does not decide the match.

## 4. Document-wide evidence (answer to point 4)
A heading that is major in a long document can only be identified with knowledge of the structure across dozens of pages. V6 therefore works in five steps:

1. **Request and scope.** `originalUserInstruction`, plus the page scope the experiment fixes (not chosen by Qwen).
2. **Document overview evidence (built by C#, observations only).** Page count and per-page statistics; lines that repeat across pages (running headers and footers); the font-size and bold distribution as statistics; numbered lines; dot-leader lines; the locations of each candidate line. No heading label is produced by C#.
3. **Qwen queries the evidence and makes provisional judgements.** Document-wide text search, whole-page text, comparison of two locations, context windows. Each query and each provisional judgement is recorded.
4. **Qwen reconciles across the document and commits.** It produces the final selection and, if the request asks for levels, a parent reference and a level in its own words. Candidates are handled in packs, but each pack request carries the document overview and the provisional judgements from step 3, so a decision is never made in isolation.
5. **C# validates and binds.** IDs and sources are exact, every cited evidence item exists in the raw transcript, parent references exist, there are no cycles, and a depth limit is respected when the request sets one (structural checks only). C# never changes or removes a decision.

The 48-line chunk is a sending unit only. Identification of a major heading depends on steps 2–4, not on the chunk.

## 5. Budget and tool rounds (answer to point 4)
The three-round limit inherited from V2–V5 is a **parameter**, not an invariant. The preflight sets the number of rounds, requests and token bounds for each track from the real document sizes, and reports:
- the number of rounds actually used, and how many requests hit the limit without a committed answer;
- the completion rate, and the cost of the preflight estimate against the cap.
If the limit is hit often, the track is reported as an incomplete method, not patched during the run.

## 6. Prompt injection (answer to point 5)
The test does not require that no decision changes. A line inserted into a document may legitimately change context. The test checks four things:
- **(a) Instruction non-execution.** Output formats or behaviour are not changed by instructions found in document text.
- **(b) Goal stability.** `originalUserInstruction` and `evaluationTrack` are unchanged in the record, and `modelTaskInterpretation` does not adopt the injected goal.
- **(c) Tool scope.** No tool is called outside the documents, the page scope and the tool list.
- **(d) Stability on unaffected candidates.** Decisions on candidates the inserted text cannot semantically affect (for example, candidates far away in another section) are unchanged. The rate of change is reported. Changes on affected candidates are reported as valid context effects, not as failures.

## 7. Renderer and vision (answer to point 6)
- The text-only V6 is not blocked by the renderer or by endpoint vision. It is designed for text and layout evidence, which is all the current pipeline uses.
- Page images are a separate branch with two gates: a renderer behind an adapter interface, installed and pinned only when the branch runs, and a check of the endpoint's image capability from the metadata the runner already fetches.
- D1 needs neither gate.

## 8. Gold per track (answer to point 6)
- **HEADING_MEMBERSHIP_DEV24:** the existing frozen all-heading Gold. Not changed.
- **MAIN_HEADINGS:** no Gold until the scope for each test is defined, with included and excluded examples, and the user approves that policy. The Gold is drafted independently of any model output. It is then approved before any prediction is made for scoring.
- **HIERARCHY:** same rules, last in order.
- **Approval record.** GPT-6 may review and propose. The user approves finally. If an AI reviewer acts under the user's delegation, the record says `AI_REVIEWER_USER_DELEGATED`, and it is never described as independent human verification.
- Post-prediction changes are reported as adjudication, with the frozen version kept beside them.

## 9. Evaluation
- Each `evaluationTrack` is scored separately, with the independent evaluator.
- HEADING_MEMBERSHIP_DEV24 allows a comparison with V4.1, and with arms A and B of section 1.
- Other tracks report no superiority claim until their Gold exists.
- Technical measures for every track: completion rate, grounded-decision rate (decisions with an evidence item from the transcript), rounds used, mismatch rate, and the four injection criteria of section 6.
- Negative results are reported as they are, and the prompt is not adjusted on the same documents to raise a score.
